# ADR-0011：百万级基础设施——单一终态架构

- 状态：已接受
- 日期：2026-08-29

## 背景

远期愿景百万节点（AI 批产 + 长尾生态），MVP 阶段几千节点。曾评估阈值触发式三档演进（<1万 per-node 直出 / 1–10万 源分片 / >10万 打包交付），被否决：基础设施从第一天按百万级终态建设，不做分层演进。

## 决策

1. **交付侧（终态形态，第一天即建）**：
   - 全图压缩边表 bundle：一次下载、永久缓存，约数十 MB 量级
   - 客户端切片：ego 网络在浏览器从 bundle 现算，不生成 per-node 切片文件
   - 搜索分片 fragment 按需加载（PageFind 式），永不整包加载索引
   - L0 元数据索引与 bundle 同步分片
2. **源侧（作者格式）**：per-node JSON 文件。低门槛贡献 UX 优先——GitHub 网页编辑器可直接修改单文件；规模由 build 吸收而非仓库结构承担。AI 批产走同格式的多文件 bulk PR
3. **build 管线按百万容量设计**：流式校验、增量构建（仅变更节点重算派生物）、实体消歧批处理（id / 别名归并检测）作为管线固定环节
4. **两层节点制**：核心节点（人工精校，全字段）与长尾存根（AI 起草，仅 L0 字段，description 留空）。Schema 新增 `origin: curated | ai-draft` 枚举，与 `last_reviewed` 共同构成信任锚
5. **运行时实现与交付格式解耦**：格式即终态；JS typed array 还是 WASM 由性能测量决定，可替换

## 后果

正面：无迁移悬崖，交付格式从第一天稳定；贡献 UX 与规模解耦。
负面：MVP 阶段即承担打包与分片基建的初始成本；per-node 文件在数十万量级后 git 可管理性下降，届时由 bulk 生成脚本吸收，作者格式不变。
